# Solana Pump Momentum & Liquidity Scalping Bot

Моментум-бот для мемкоинов **Pump.fun** в сети Solana (короткий свинг,
удержание до `MAX_HOLD_SECONDS=180` c). Считывает поток сделок через
WebSocket (Helius), жёстко фильтрует ликвидность и безопасность контракта
(контур отбора до торговли), входит на импульсе объёма. Выход — пять
параллельных триггеров, срабатывает первый: каскадный тейк-профит
(+30% / +50%), трейлинг-стоп (10% от пика), жёсткий стоп-лосс (−30%),
детектор затухания импульса (крупная продажа / падение Buy-Sell Ratio),
таймаут удержания (180 c). Типичное удержание задаёт рынок: затухание
импульса закрывает позицию за секунды, «мёртвый» токен держится до таймаута.

Поддерживаются обе стадии жизни токена Pump.fun: bonding curve (прямые
инструкции) и PumpSwap AMM после миграции (через Jupiter fallback).
Raydium по умолчанию **отключён** (`ENABLED_DEX=pump_fun`); вернуть его можно
значением `ENABLED_DEX=pump_fun,raydium` — прямых Raydium-инструкций в коде
нет, сделки по таким пулам всегда идут через Jupiter.

## Возможности

- **Потоковый листенер**: `logsSubscribe` + `accountSubscribe` (Helius WebSocket) с
  авто-реконнектом и экспоненциальным backoff; события Pump.fun разбираются
  из Anchor-логов (`TradeEvent`), для AMM-пулов сделки синтезируются из дельт
  vault-балансов.
- **Liquidity Guard**: для bonding curve — порог по **реальным** резервам
  (`MIN_REAL_POOL_SOL`; виртуальный резерв кривой всегда ≥ 30 SOL, поэтому
  порог по виртуальным был бы фиктивен), для AMM-пулов — `MIN_POOL_SOL`;
  предельный Price Impact (`MAX_PRICE_IMPACT_PCT`); расчёт `min_tokens_out`
  по формуле постоянного произведения `x·y = k` с дисконтом
  `BUY_SLIPPAGE_PCT`. Комиссии по стадии: кривая 1%, PumpSwap AMM 125 bps
  (консервативно к Dynamic Fees V1).
- **Контур отбора токенов до торговли**: каждое новое имя монеты при первом
  обнаружении проходит фоновую проверку контракта (mint/freeze authority, LP
  burn) и получает вердикт `approved/rejected` в SQLite-аудит; горячий путь
  торговли не делает ни одного RPC-запроса по безопасности, а отклонённые
  токены вычищаются из реестра пулов и индикаторов.
- **Momentum Trigger**: Buy/Sell Ratio и Volume Velocity в скользящем окне.
- **Движок выходов**: каскадный TP (+30% / +50%), trailing stop (откат от пика),
  hard stop-loss (−30%), детектор крупных продаж и падения Buy/Sell Ratio,
  таймаут удержания (`MAX_HOLD_SECONDS`, по умолчанию 180 c).
- **Два канала отправки** (`EXECUTION_VENUE`): `rpc` (по умолчанию) — обычная
  транзакция через Helius без Jito-чаевых, подтверждение через
  `getSignatureStatuses`; `jito` — бандл с memo `jitodontfront` и чаевыми
  валидатору, подтверждение через `getBundleStatuses`. В обоих каналах позиция
  учитывается только после подтверждения (`JITO_REQUIRE_CONFIRMATION`).
- **Лестница выхода**: первая попытка продажи с дисконтом `SELL_SLIPPAGE_PCT`;
  если транзакция откатилась по порогу — свежая котировка и повтор с
  `min_sol_output = 0`, чтобы выход исполнялся в любом случае (повтор только
  при заведомо неотправленной транзакции; при неопределённом статусе повтор
  опасен двойной продажей).
- **Jupiter fallback** (опция, по умолчанию **выключен**): резервный маршрут
  через агрегатор (`/swap-instructions`) для токенов, мигрировавших с bonding
  curve на PumpSwap AMM. Без него бот торгует только токены на кривой; продажа
  позиции, в которой токен успел мигрировать, завершится ошибкой — включайте
  `USE_JUPITER_FALLBACK=true` для live-торговли с удержанием позиций.
- **Персистентность позиций**: SQLite (`PORTFOLIO_DB_PATH`, WAL, write-through) —
  открытые позиции переживают рестарт, бот продолжает вести их выходы; dry-run
  пишет в отдельную БД (`data/bot_dry.db`).
- **Несколько позиций**: токенов в работе — неограниченно; лимитируется
  число входов на один mint (`MAX_ENTRIES_PER_MINT=4`, вход + усреднения)
  и опциональный лимит капитала `CAPITAL_SOL`.
- **Веб-дашборд с ручным управлением**: вся картина торговли в браузере
  (`http://127.0.0.1:8787`) — позиции с нереализованным PnL, кривая
  реализованного PnL, покупки/продажи и события/сек, win-rate, контур
  отбора с причинами отказов, латентность p50/p95, хвост лога (200 строк,
  копируется). Плюс **кнопки ручных сделок** с подтверждением: «✕ закрыть»
  и «＋ усреднить» у каждой позиции, большая «ПРОДАТЬ ВСЁ», встроенный
  **бэктест** (по ссылке pump.fun или CSV) и **Старт/Останов торговли** —
  через тот же исполнитель и лестницу выхода, с per-mint блокировкой от
  гонок и аутентификацией (`DASHBOARD_USER/PASSWORD`). SSE-обновление
  раз в 2 c, без новых зависимостей (aiohttp уже в проекте); слушает
  `127.0.0.1`, отключается `--no-dashboard`.
- **Бэктестер**: прогон исторических CSV через те же фильтры, стратегию и
  движок решений (переиспользует `MomentumTrader`, а не копию логики).

## Архитектура

Живой путь события (dry-run отличается только исполнителем):

```
Helius WS (logsSubscribe: Pump.fun, PumpSwap AMM; accountSubscribe: пулы)
  │
  ▼
core/listener.py  PoolStreamListener ── парсинг Anchor-логов в TradeEvent
  │                 (bonding curve: дискриминатор TradeEvent;
  │                  AMM: синтез сделок из дельт vault-ов)
  │
  ├─[новый mint]──► core/screening.py  TokenScreeningService ── КОНТУР ОТБОРА
  │                   очередь → проверка контракта по правилам
  │                   (mint/freeze authority, LP burn) → вердикт
  │                   в кэш + SQLite token_screening (аудит, рестарт);
  │                   rejected → пул вычищается из реестра/индикаторов
  ▼
asyncio.Queue (8192, put_nowait — WS-колбэк не блокируется)
  │
  ▼
core/pipeline.py  LivePipeline ── consume-loop, обслуживание реестра пулов,
  │                 восстановление открытых позиций из БД при старте
  ▼
core/trader.py  MomentumTrader ── единственная точка решений:
  │               индикаторы → фильтры → стратегия → заявка → исполнитель
  │               (выход: лестница 25% → floor 0, см. «Ключевые решения»)
  ├─► analytics/indicators.py   скользящие окна (ratio, velocity, цена)
  ├─► core/screening.py provider  готовый вердикт из кэша (ноль RPC):
  │     approved → TokenSecurity; rejected/нет вердикта → None (fail-closed)
  ├─► filters/                  LiquidityGuard, SecurityGuard (страховка)
  ├─► strategies/momentum_pump.py   триггеры входа/выхода (чистая логика)
  ├─► core/orders.py            котировки AMM и сборка Buy/SellOrder
  └─► core/executor.py          план свапа → компиляция v0 → подпись → канал
        ├─ core/tx_builder.py   инструкции bonding curve Pump.fun
        ├─ core/jupiter.py      fallback-маршрут (AMM/миграция, опция)
        ├─ venue=rpc:  client.py sendTransaction + getSignatureStatuses
        ├─ venue=jito: jito.py sendBundle + getBundleStatuses
        └─ core/dry_run.py      бумажное исполнение (--dry-run, бэктест)
  │
  ▼
core/portfolio.py  PortfolioManager ── memory-ledger позиций
  └─► core/persistence.py  PortfolioStore ── SQLite write-through
        (таблицы positions / closed_trades / token_screening;
         рестарт → load_open_positions + load_persisted вердикты)
```

Исполнители подключаются инъекцией через Protocol `TraderExecutor`
(`core/orders.py`), поэтому live, dry-run и бэктест используют одну и ту же
математику котировок и один движок решений. Все сетевые данные безопасности —
`core/security.py` (`TokenSecurityResolver`, RPC + TTL-кэш) — подаются
трейдеру по требованию перед входом.

## Установка

Требуется Python 3.11+.

```bash
python -m venv .venv

# Windows
.venv\Scripts\activate
# Linux / macOS
source .venv/bin/activate

pip install -r requirements.txt
cp .env.example .env   # заполните HELIUS_API_KEY и кошелёк
```

### Кошелёк

Задайте один из вариантов:

- `WALLET_PRIVATE_KEY` — приватный ключ в base58, либо
- `WALLET_KEYPAIR_PATH` — путь к JSON keypair (`solana-keygen new -o keys/id.json`).

## Ключевые решения: причины, реализация, математика

### 1. Канал отправки `EXECUTION_VENUE=rpc` (Helius вместо Jito)

**Причины отказа от Jito (по умолчанию):**

* Jito-чаевые `JITO_TIP_SOL=0.005` при входе `TRADE_AMOUNT_SOL=0.5` — это
  1% ордера на каждую сторону, **2% за круг** — больше комиссии пула;
  на этапе отладки стратегии это чистый дар валидаторам;
* Helius RPC достаточен для текущего горизонта (холды до минут, не
  microseconds-HFT); ко-локация с block engine значима только для
  «первого слота», что не является текущей целью.

**Что теряем (осознанно):** анти-сэндвич-защиту бандлов и приоритет
приземления (региональный block engine + валидаторы с долей Jito). На
bonding curve Pump.fun сэндвич-риск ниже, чем на AMM, но фронтранн покупок
на активном пампе существует. Публичный Helius-эндпоинт также добавляет
латентности — эдж становится тоньше.

**Что НЕ теряем:** атомарность. Одиночная транзакция в Solana атомарна сама
по себе; бандлы дают атомарность только для *цепочек* транзакций, а бот
отправляет ровно одну транзакцию на ордер.

**Реализация** (`core/executor.py`):

* `venue=rpc`: инструкции = Compute Budget + свап (без memo `jitodontfront`
  и без tip-инструкции — см. `_compose_instructions(..., tip_account=None)`);
  отправка `sendTransaction` с `skipPreflight=true, maxRetries=0`;
  подтверждение — опрос `getSignatureStatuses`: появление
  `confirmationStatus` (любой из `processed`/`confirmed`/`finalized`) —
  транзакция в блоке; `err` — немедленный отказ; таймаут `JITO_CONFIRM_TIMEOUT_SECONDS`.
* `venue=jito`: прежний путь — memo + Compute Budget + свап + tip,
  `sendBundle`, подтверждение `getBundleStatuses` до `Landed`.
* Оба канала: при **таймауте** подтверждения — CRITICAL-лог с подписью
  (транзакция могла приземлиться после таймаута — проверять вручную), позиция
  не открывается / продажа не учитывается (`OrderResult.confirmed=false`).
  Таймауты/интервалы опроса общие для обоих каналов.

### 2. Лестница выхода: `SELL_SLIPPAGE_PCT` → floor 0

**Проблема, которую решаем.** Жёсткий `min_sol_output` в инструкции продажи
роняет транзакцию, если фактический выход оказался ниже «котировка − 25%».
На тонком эдже это происходит регулярно: между сборкой транзакции и её
приземлением (~1 слот) цена может уйти против сильнее дисконта — особенно на
раг-свече или мощном дампе. Повторы роняются повторно, позиция зависает.
Для продажи это фатально: покупка, которая не исполнилась, теряет лишь
возможность, продажа **обязана** исполниться.

**Почему не «плоский ноль» с первой попытки.** `min_sol_output` — последний
предохранитель от наших собственных ошибок: протухшие резервы в снимке пула
(`PoolInfo`) или баг котировки. С floor 0 такой сценарий молча продаёт
позицию по любой цене. С холдом 180 c снапшот резервов живёт дольше — риск
выше, чем при скальпе на 1–3 c.

**Реализация** (`core/trader.py`, `_handle_exit`):

1. Попытка 1 — дисконт `SELL_SLIPPAGE_PCT` (25%).
2. Если `success=False` (транзакция **заведомо** не отправлена или on-chain
   отказ) — свежая котировка и попытка 2 с `min_sol_output=0`.
3. Если `success=True, confirmed=False` (статус неизвестен — транзакция
   могла приземлиться позже) — повтор **запрещён**: риск двойной продажи.
   Пул ставится на паузу `RETRY_COOLDOWN_SECONDS`, позиция остаётся открытой.
4. После двух неудач — пауза на пул, повтор на следующем событии.

**Нюанс математики (важно).** В терминах `utils/amm.py` «0% проскальзывания»
**не равно** floor 0: `min_out_with_slippage(x, 0)` возвращает `x` —
требование получить **ровно** котировку, что строже, чем дисконт 25%. Такой
ордер не приземлится почти никогда. Поэтому настоящий floor=0 ставится явно:
котировка пересчитывается с дисконтом 0, а порог обнуляется
`dataclasses.replace(quote, min_amount_out=0)`. Разделение смыслов:
`slippage_pct` — *относительный* дисконт котировки; `min_amount_out` —
*абсолютный* минимум выхода. Тест `test_execution.py` фиксирует контракт:
первая попытка `min_amount_out > 0`, вторая — `== 0`.

### 3. Стоп 30%, холд 180 c и Jupiter для live

**Стоп `HARD_STOP_LOSS_PCT` 12% → 30%.** 12% внутри минутных колебаний
мемкоина — систематические ложные стопы («смерть тысячей порезов»): токен
выбивает по шуму, после чего продолжает пампить. 30% соразмерен волатильности
и холду 180 c.

*Математика безубыточности сдвинулась.* Луз ≈ −30% вложенного; вин через
каскад TP (TP1 +30% на половину + TP2 +50% на остаток) ≈ +40% SOL. Порог
win-rate ≈ 30/70 ≈ **43%** (при стопе 12% был ≈ 23%). Т.е. требование к
качеству входов выросло вдвое — контур отбора и momentum-фильтры теперь
несут основной груз. Кроме того, стоп — это **сигнал, а не гарантия цены**:
при раг-свече сквозь стоп и floor-0-повторе реализованный убыток может
превысить 30% (исполнение по фактическим −60…−80%). Это осознанная цена
принципа «продажа всегда исполняется».

**Холд `MAX_HOLD_SECONDS` 30 → 180 c.** Горизонт смещается от микроскальпа
к короткому свингу. Следствия:

* **миграция токена на AMM за 3 минуты — штатный сценарий** (кривая часто
  завершается именно на пампе). Прямые инструкции кривой после миграции
  перестают работать, поэтому для live включён `USE_JUPITER_FALLBACK=true`:
  без fallback продажа мигрировавшей позиции невозможна **в принципе** —
  никакая лестница тут не поможет, маршрут отсутствует целиком;
* большинство выходов теперь делает trailing stop (10% от пика) и
  exhaustion-детектор; TP-каскад и max-hold — хвостовые защиты. Порог
  `TRAILING_STOP_PCT` — кандидат на калибровку по живым данным;
* при гейте ликвидности (`MIN_REAL_POOL_SOL=40`) и окне надёжности 5 c
  оборот капитала ниже, но и доля откровенного шлака во входах — меньше.

### 3.1. Семантика входов: один mint до 4 входов, мёртвые токены не блокируют

- **Лимит по mint, не по токенам.** Лимит `MAX_ENTRIES_PER_MINT=4` действует
  на число входов (вход + усреднения) по одному токену; самих токенов в
  работе может быть сколько угодно. Авто-усреднение: если по открытой позиции
  выходные триггеры молчат, а стратегия снова даёт ENTER (все гейты входа
  применяются полностью) — бот докупает `TRADE_AMOUNT_SOL`, поднимая
  средневзвешенную цену входа. Ручное «＋ усреднить» подчиняется тому же
  лимиту. PnL считается по аккумулированному `entry_sol` и фактическим
  возвратам — несколько входов по одному mint корректно агрегируются в одну
  позицию и одну запись `closed_trades`.
- **Окно надёжности.** Входы/усреднения разрешены только по токенам старше
  `TOKEN_RELIABLE_SECONDS` (5 c) с момента обнаружения пула — за это время
  видно, живёт ли токен, и отсеивается часть мгновенных скам-разгоний.
- **Свип устаревших позиций.** Событийный выход по `MAX_HOLD_SECONDS`
  срабатывает только когда по токену идут события. Фоновый свип (раз в 5 c)
  закрывает позиции старше `MAX_HOLD_SECONDS` и в live: попытка продажи, а
  если продать нечем (пул мёртв) — учётное закрытие **полным убытком**
  (`exit_reason=max_hold_unsellable`): строка открытой позиции удаляется из
  БД, в `closed_trades` пишется убыток в размере вложенного SOL. В live при
  этом пишется CRITICAL: токены могли остаться в кошельке.

### 4. Сверка с практикой рынка (GMGN, снайпер-боты, документация Pump.fun)

Калибровка по открытым источникам: официальные docs GMGN (fees/settings),
механика bonding curve Pump.fun (виртуальные/реальные резервы), практика
Solana-снайперов (FluxBeam/Trojan/RPCFast-обзоры), Helius Sender/SWQoS.

**Priority fee.** Дефолт 100,000 µL/CU при CU 200,000 давал всего
**0.00002 SOL** приоритетки на транзакцию. Практика: GMGN — минимум
0.0001 SOL, рекомендуемые суммарные 0.002–0.005 SOL (авто-стратегии —
0.006+); снайперы — 0.0005–0.005 SOL. Установлен `PRIORITY_FEE_MICRO_LAMPORTS
= 1,000,000` (≈0.0002 SOL/tx) как стартовая точка: заметно выше «очереди»,
существенно дешевле полного снайперского уровня. Дальнейший подъём — по
доле неподтверждённых транзакций в живом прогоне.

**Реальные резервы кривой.** Виртуальный резерв bonding curve Pump.fun
всегда = реальные + 30 SOL (реальные стартуют с нуля, градуация ~85 SOL
реальных). Прежний порог `MIN_POOL_SOL=30` по виртуальному резерву проходил
для **каждого** токена с момента создания — фильтр был фиктивен. Введён
`MIN_REAL_POOL_SOL` (реальные ≥ порога ⇒ токен собрал существенные деньги; текущее значение 40 SOL);
для AMM-пулов остался `MIN_POOL_SOL=30` по полному резерву.

**Комиссии PumpSwap.** Bonding curve — 1% (у нас 100 bps, верно). PumpSwap
после миграции: 0.25% базовая, но с Dynamic Fees V1 — ступенчатая шкала по
market cap (свежеградуированные ~1.25%). Для AMM-стадии Pump.fun-токенов
принято 125 bps (консервативно к свежим выпускам); для Jupiter-маршрута
фактические комиссии считает сам агрегатор — наша оценка влияет только на
предрасчёт price impact при входе.

**Buy slippage 20 → 15.** Без MEV-защиты (venue=rpc) сообщество советует
компактный допуск (1–10%); GMGN допускает 30–50%, но у них анти-MEV включён.
15% — компромисс: ущерб сэндвича ограничен `max_sol_cost`, а вход у нас
импульсный, не слепой снип первого блока.

### 5. Бэктест в дашборде

Полукруглая кнопка **⌗ BACKTEST** под окном лога раскрывает блок запуска
бэктеста прямо из браузера. Два источника данных:

* **Ссылка pump.fun / mint** — бот сам выводит bonding curve, забирает
  историю сделок кривой через Helius (getSignaturesForAddress +
  getTransaction, лимит `max_tx` ≤ 1000), распарсивает настоящие
  TradeEvent-логи и сеет начальное состояние виртуальными резервами
  самого раннего события. Ограничение: токен на кривой; для мигрировавших
  нужен экспорт сделок AMM (позже);
* **CSV-текст** канонического формата реплея (кнопка «демо-CSV» заполняет
  форму примером импульс-сценария).

Параметры запуска: размер входа, окна входа/выхода, макс. позиций,
начальные резервы (для CSV). Результат — карточки (сделки, win-rate,
PnL, просадка, лучший/худший трейд), полосы причин выхода и таблица
сделок. Движок — тот же `MomentumTrader` + dry-run, что и в live,
поэтому результат отражает реальную логику. OHLCV-свечи не поддержаны
сознательно: движок событийный, свеча не несёт последовательности
buy/sell для momentum-окон.

**Кнопка «ОСТАНОВИТЬ».** Долгие прогоны (сотни транзакций) можно прервать:
кооперативная отмена через cancel_event — цикл завершается на ближайшем
событии, позиции корректно финализируются (`close_all`), и возвращается
**частичная статистика** по пройденной части с пометкой «остановлено».
Защита от ложного стопа: принимается только `run_id` текущего запуска.
Каждые 25 событий цикл отдаёт управление loop'у — SSE и кнопки остаются
отзывчивыми во время прогона.

### 6. Стабильность WS-стрима и корректные единицы цены

**Коллизия Anchor-дискриминаторов (фикс 2026-11-09).** PumpSwap (`pAMM…`)
называет своё Anchor-событие тоже `TradeEvent` — первые 8 байт совпадают с
событием bonding curve, но раскладка полей другая. Декодирование логов
PumpSwap bonding-curve декодером давало мусорные mint/резервы/время
(в статистику попадали сделки с PnL до +33M SOL и удержанием 10^18 c).
Логи теперь гейтуются по программе-источнику: bonding-curve декодер
применяется только к `6EF8…F6P`; плюс санити-гейт полей (время живое,
ордер ≤ 10k SOL, виртуальный резерв ≥ 30 SOL).


**Читатель сокета стартует до переподписки.** Исходный порядок в
`_run_forever` — «переподписка → читатель»: ответы сервера на
logsSubscribe/accountSubscribe никто не читал, каждая подписка падала по
таймауту 10 c и не восстанавливалась (поток событий умирал после первого
реконнекта), а keepalive-ping оставался без ответа → разрывы каждые ~60 c.
Фикс: `reader_task` создаётся сразу после подключения, переподписка идёт
при живом читателе; счётчик уведомлений на соединение + WARNING при
разрыве «до первого уведомления» делают такой случай видимым в логе.

**Единицы цены выхода у продаж.** `execution_price()` была ориентирована на
BUY-котировку (`amount_out` = токены, `amount_in` = лямпорты); для SELL
`amount_in`/`amount_out` меняются местами, и в `closed_trades.exit_price`
записывались «лямпорты за raw-токен» (~2.88) вместо SOL/токен (~3.5e-7).
На PnL не влияло (он считается по invested/returned), но портил
диагностику и таблицы бэктеста. Фикс: цена выхода продающих сделок
считается из фактического результата — `sol_amount / token_amount`.

**Отложенные улучшения** (следующие итерации): кэш blockhash в исполнителе
(−50–150 мс на ордер), опрос подтверждений 0.2–0.3 c, интеграция Helius
Sender (SWQoS-роутинг) как venue-вариант, фильтр концентрации холдеров
(top-10 %) в контур отбора, `TRAILING_STOP_PCT` 15% по итогам живой
калибровки.

### Веб-дашборд

Пока бот работает, откройте `http://127.0.0.1:8787`. Одна страница:
шапка (режим/сеть/venue/uptime/позиции), таблица открытых позиций
(цена входа/текущая, PnL%, пик, холд, TP1), карточка «Сессия» (закрытые
сделки, win-rate с полосой, PnL, лучший/худший трейд, ордера ок/сбой),
«Поток» (события/сек, покупки/продажи с полосами, пулы, очередь, потери),
«Отбор токенов» (ждут/одобрено/отклонено + последние отказы с причинами),
«Латентность» (p50/p95 по этапам), график реализованного PnL и хвост лога
(200 строк; кнопка «Очистить лог» чистит только панель — файловые логи
не трогаются; выделение текста приостанавливает перерисовку панели, чтобы
спокойно скопировать нужное). Данные пушатся по SSE раз в 2 c, страница
перерисовывается без перезагрузки.
Дашборд стартует до сети: страница доступна сразу, даже если WS ещё
подключается. На VPS — ssh-туннель `ssh -L 8787:127.0.0.1:8787 user@vps`;
открытие `0.0.0.0` наружу — только с закрытым фаерволом.
Занятый порт не валит бота: предупреждение в логе, торговля продолжается.

**Старт/Останов бота.** В шапке — зелёная кнопка «Старт бота» и красная
«Остановить торговлю» (мягкая остановка: подписки закрываются, расход
кредитов Helius прекращается, дашборд продолжает работать, открытые
позиции остаются в БД без управления до возобновления). Полный останов
процесса — красная «ОСТАНОВИТЬ БОТА» (для VPS: юнит с `Restart=on-failure`
не перезапустит чистую остановку). Требуется аутентификация.

**Переключение режима dry ↔ LIVE.** Клик по бейджу «mainnet-beta» в шапке
всплывает подсказкой и переводит торговлю между режимами: в LIVE — синий
контур на бейдже, dry-run «гаснет»; обратно в DRY-RUN — повторный клик.
Защиты: при открытых позициях смена режима отклоняется (сначала
«ПРОДАТЬ ВСЁ»); переход в LIVE требует настроенного кошелька. У режимов
разные БД (`bot_dry.db` / `bot.db`) — статистика не смешивается.

**Аутентификация и ручные сделки.** Вход — логин/пароль из
`DASHBOARD_USER`/`DASHBOARD_PASSWORD` (по умолчанию `home`/`123` —
**смените пароль** перед использованием). После входа выдаётся
сессионный токен на 12 ч. Кнопки: «✕ закрыть» продаёт позицию целиком
через исполнитель и лестницу выхода (floor 0 на повторе) с пометкой
`manual`; «＋ усреднить» докупает `TRADE_AMOUNT_SOL` к позиции
средневзвешенной ценой; «ПРОДАТЬ ВСЁ» закрывает все позиции подряд.
Все операции проходят через per-mint блокировки (нет гонок с
автостратегией) и write-through БД: закрытие удаляет строку позиции и
пишет `closed_trades`, усреднение обновляет цену входа UPSERT-ом —
«зависших» записей не остаётся. Неудачная операция оставляет позицию
нетронутой и показывает ошибку в статусной строке.

Открытые позиции по умолчанию **не** закрываются при остановке и восстанавливаются
при следующем запуске из SQLite-БД (`PORTFOLIO_DB_PATH`; dry-run пишет в
отдельную `PORTFOLIO_DB_DRY_PATH`; пустой `PORTFOLIO_DB_PATH` отключает
персистентность).

## Важные предупреждения

1. **Продакшен — только Linux VPS** рядом с RPC-нодой (Frankfurt/Amsterdam):
   канал `rpc` идёт через публичный Helius-эндпоинт, каждая сотня миллисекунд
   RTT съедает эдж.
2. **Проскальзывание 20% (вход) / 25% (выход)** — допуск инструкции, а не
   фактическая потеря; выход дополнен лестницей до floor 0 (см. «Ключевые
   решения»), поэтому реализованный убыток на стопе может превысить
   `HARD_STOP_LOSS_PCT` при раг-свече.
3. **Rate limits**: Helius на плане могут быть лимиты запросов/сек — при
   интенсивном стриме следите за логами реконнектов; Jito (если вернёте
   `EXECUTION_VENUE=jito`) — 1 запрос/сек на IP на регион.
4. **Бэктест обязателен** перед торговлей реальными средствами: пороги
   (стоп 30%, trailing 10%, ratio/velocity) требуют калибровки на живых
   данных, а математика win-rate изменилась вместе со стопом (≈43% порог).
